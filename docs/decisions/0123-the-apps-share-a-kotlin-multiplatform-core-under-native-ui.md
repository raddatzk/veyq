# ADR 0123 — The apps share a Kotlin Multiplatform core under a native UI per platform

- Status: Accepted
- Built: partly (not built: most writes, the applications' own screens but Expenses' open Pot)
- Date: 2026-11-08

## Context

V2 is the native apps (owner 2026-11-07): iOS, macOS (one Apple app) and Android, each with the platform's own UI, on
one shared base. Their navigation is [ADR 0122](0122-one-app-holds-every-application-the-drawer-chooses-the-bar-belongs-to-it.md).
The web's crypto suite is TypeScript (`@veyq/crypto`), and the root `CLAUDE.md` calls a second copy of key-material
logic a security defect: a native client cannot run that package, so the question is not whether a second
implementation exists but what holds it to the first.

## Decision

1. **`src/mobile/` is one Gradle build of its own** (like `src/backend/`, never included by the root launcher):
   `core`, the Kotlin Multiplatform base (targets: the JVM, which the Android app consumes, and `iosArm64`,
   `iosSimulatorArm64`, `macosArm64`, packed into one `VeyqCore.xcframework`); `android`, the Android app in Compose;
   `apple`, one SwiftUI target for iOS and macOS, its Xcode project generated by XcodeGen from `apple/project.yml` and
   never committed. UI is never shared; the navigation state ([ADR 0122](0122-one-app-holds-every-application-the-drawer-chooses-the-bar-belongs-to-it.md)'s
   `Shell`, the list rule) is, so both platforms render one model.

2. **The suite is ported once, to Kotlin, and held to the vectors.** `core` carries the v1 protocol — the seal
   contexts, the three envelopes, X-Wing's key expansion and combiner (draft-connolly-cfrg-xwing-kem-11), the KEKs,
   the auth derivation, the Secret Key's text form, the grant statement — once, in common code. It is held to
   `contracts/crypto/vectors/v1.json` by `Conformance`, which lives in main code so a platform can run it over its own
   primitives, and whose test includes a bite: a primitive off by one byte must turn it red. The vectors are the one
   gate both implementations answer to, as the web's package already does; a vector the app fails is a red build, not
   a seal that silently fails to open.

3. **Only the raw primitives are per platform,** behind one interface (`Primitives`): AES-256-GCM, HKDF- and
   HMAC-SHA256, SHA-256, Argon2id, Ed25519, X25519, ML-KEM-768 (`KeyGen_internal(d, z)`, deterministic encapsulation
   for the vectors). SHA3-256 and SHAKE256 come from KotlinCrypto in common code. On the JVM and Android they are
   BouncyCastle's lightweight API (no JCA provider to register). On the Apple platforms they are **libsodium** (1.0.22
   added ML-KEM-768 and X-Wing to Argon2id, Ed25519, X25519, HKDF and AES-256-GCM), linked through cinterop, so the
   Apple code is Kotlin too and the same `Conformance` runs on it; `core/sodium/build_libsodium.py` builds it from the
   release tarball, checked against a pinned SHA-256.

4. **The API client is generated** from `contracts/api` by the generator version the repository pins
   (`scripts/validate_build_input_pins.py`), `kotlin` with the `multiplatform` library, into `core`'s build. The
   specs' server-side annotations (`x-*-extra-annotation`: Jakarta validation, Jackson) are dropped after generation;
   any trace of a backend package left in the output fails the build. Core's specs, the ones a member's app calls;
   an application's spec joins with that application's screens, into packages of its own (`api.expenses`), so its
   models never meet core's. An application's code in `core` is a package of its own too (`expenses`), which uses
   core's session and is never used by it, as on the web ([ADR 0079](0079-veyq-is-a-platform-memories-is-its-first-application.md)).

5. **The session is the web's flow, call for call:** `/api/setup` and its major (the one hard gate before sign-in,
   [ADR 0085](0085-one-major-moved-on-a-yearly-train.md), compiled from `VERSION`), the login challenge answered by the
   Ed25519 key of the Argon2id auth seed ([ADR 0003](0003-operator-blind-password-auth.md)), the refresh token in the
   body rather than a cookie, one refresh in flight at a time ([ADR 0004](0004-session-tokens.md)), the PASSWORD wrap
   opened with password and Secret Key, then each scope grant verified before it is opened. **A grant is judged as the
   web judges it** (`core/…/session/Grants.kt`, a port of `openOwnGrant` and `verifyOwnGrant`): its signature first,
   then for another member's grant that member's key chain anchored from the head this account pinned
   ([ADR 0028](0028-identity-authenticity-tofu-verification.md) decision 2) in the account's synced pin store, written byte for byte as the
   web writes it ([ADR 0104](0104-the-identity-pin-store-is-one-sealed-entry-per-pin-under-a-sealed-head.md)); a group's granter judged by
   their standing in the tenant's member list ([ADR 0111](0111-an-invitee-grants-itself-a-rotator-re-keys-its-own-scopes-and-a-key-chain-anchors-trust.md) decisions 12, 15 and 21, `session/Anchoring.kt`): an owner without a
   join record by the pin, a member who joined by invite by their join record — opened with the tenant key, its
   three signatures verified, its signer an owner anchored in turn (with that owner's endorsement where the key that
   rooted it is retired), their chain walked from the step it names —, anyone else refused; a retired key only at or
   below this device's floor; a later epoch only through the succession statements from the key this device held
   ([ADR 0115](0115-a-scope-key-is-replaced-never-chained.md) decision 5). The floor and the held keys are this device's
   own trust marks, never synced, in the platform's preferences (no secret). What a start may skip is decision 8.
   **An account is one server's; a tenant is a domain of it** (owner 2026-11-08: one server gives several tenants, and
   the app connects to several servers). A session is the account's, not a tenant's (ADR 0004), so one sign-in opens
   every tenant the account holds there (`listMyTenants`), each at its own domain on the sign-in's scheme and port,
   since the server picks the tenant from the Host; another server is another sign-in, held beside the first. The same
   user on the same server is one connection however often it signs in. The connections live in memory with the keys.

6. **A dev tenant is reached by its name.** The tenant is picked from the Host ([scopes-and-tenancy](../crosscutting/scopes-and-tenancy.md)),
   and a dev tenant is a `*.localhost` name: the Android debug build resolves such a name to the emulator's view of
   the developer's machine (10.0.2.2) and keeps it in the Host header; the Apple app reaches it as the Mac resolves it,
   with an App Transport Security exception for `localhost` only. The web's `?devlogin` has one counterpart per
   platform, in debug builds only: `android/devlogin.py` hands the seeded principal from `.run/.env` to the app as
   launch extras, `apple/devlogin.py` as the environment of a simulator launch; a release build has no such door.

7. **The apps wear the web's theme on their platforms' own controls** (owner 2026-11-08: native UI and UX, the web's
   theming). The web's colour roles ([ui-web-styleguide](../crosscutting/ui-web-styleguide.md)) and its brand mark
   are read, never copied: `src/mobile/theme/generate_theme.py` turns `src/web/src/styles/base.css` (light and dark)
   and `src/web/src/assets/brand/logo-{light,dark}.svg` into a Kotlin palette (`core`), Android resources (window,
   splash, adaptive launcher icon with its monochrome layer) and an asset catalog (a colour set per role, the mark,
   the app icon for iOS and macOS, rendered by macOS' own Quick Look), each at build time; its CSS reader is
   `scripts/validate_web_contrast.py`'s, so the WCAG floors the web's roles are held to hold for the apps' too. The
   roles keep the styleguide's meanings: the accent is the brand, the selection and the tint (Material's primary, the
   Apple tint); the green `primary` is creating and confirming only (Material's tertiary). The type stays the
   platform's (the web bundles no font); the web's weights, its section label, its radii (6, 10, 12) and its leading
   tile are taken. Icons are each platform's own symbols drawn with the web's motifs (`images`, `file`, `inbox`,
   `wallet`, `folder`), not Lucide.

8. **A device is trusted as the web trusts one, and staying signed in waits behind the person** (owner 2026-11-08:
   the web's two tiers, plus the platform's biometrics). After a sign-in with the Secret Key the app enrols one of the
   web's two device wraps of the Master Key ([ADR 0005](0005-unlock-methods-and-device-trust.md), `POST /api/account/wraps`),
   one per account per device, the new one recorded before the old one is deleted:
   - **By default a `DEVICE` wrap:** the KEK is Argon2id over the device factor and the password, the factor the HMAC
     of `veyq/v1/device-bind` under a key the Android Keystore or the Keychain holds and never hands out. The next
     start needs the password, never again the Secret Key. A signed-in session is not kept: each start logs in.
   - **"Stay signed in" is an explicit choice** (ADR 0005 § 13, said with what it costs): a `DEVICE_KEY` wrap, the
     Master Key AES-256-GCM sealed under one unlock key of the app that opens only after the person authenticated —
     a strong biometric or the device's code (Android: `setUserAuthenticationParameters`, a new biometric enrolment
     voids it; Apple: `.userPresence`, asked through LocalAuthentication first) — with the iv as the wrap's
     `kdfParams` and the web's associated data. The refresh token, which reaches the server and nothing sealed, is
     kept without asking (Keystore-sealed preferences, the Keychain), and each rotated one at once. One
     authentication within a short window resumes every remembered account of a start.
   What a device keeps per account is a record (server, email, account, method, the wrap's id, its key's alias): the
   wrap is found among the served ones by its id, and a wrap the server withholds is no reason to forget it (the
   person signs in with the Secret Key instead). A refresh the server refuses ends the remembered session on the
   device; one it cannot answer keeps it. Signing out ends staying signed in (its wrap deleted, its token and key
   gone) and keeps the password trust, as on the web; "Stop trusting this device" ends either. Every unlock and every
   enrolment names the device in the account's device register (write moments 1 and 2 of en.account.device-register,
   its label the device's model), so a person's other device can find this one's saved key and remove it
   ([ADR 0058](0058-revoke-never-takes-key-material.md)). iOS keeps Keychain items when an app is deleted: a first start
   after an installation removes them.

## Consequences

- **Built of the applications: Expenses' open Pot** — its entries, overview and settings as the web's Pot shows them,
  its entries added and edited in the web's editor (an expense, a refund or a transfer; payers, items with their own
  splits and the rest's split by shares, percent or amount, another currency at a rate the day's table fills where the
  tenant names the service (`expenses/ExchangeRates.kt`, the web's `exchangeRates.ts`: one table a device and day, kept in
  the device's store, a day whose request failed not asked again, the cross rate exact; `ExchangeRatesTest`) or typed,
  the shares in the base
  currency as the save seals them; an edit stated on the revision it was shown, so a concurrent one is read, not
  overwritten), whose every rule is core's (`expenses/EntryForm.kt`, the web's `entryForm.ts`: every vector entry
  survives the form unchanged and the Pot written from those forms computes the vectors' balances; `EntryFormTest`, each
  rule killed by a mutation), an entry deleted, kept in the Pot's deleted entries and restored until its tombstone's
  `purgeAfter`, its history read newest first with each revision's writer — a member by the directory's name; a link
  guest's sealed name is not opened in the app, so a guest reads as "someone" —, and a settle-up suggestion recorded
  as a transfer (`PotViewEntriesTest`), and its people managed as the web's people panel does (a name or a
  space member added, a name renamed, a settled person deactivated, deleted or removed; `PotViewPeopleTest`), a member
  read by the current name core's directory opens (`session/People.kt`, the web's `core/people/directory.ts`: the
  `member-name` field under its value key, from the tenant's member list), and its settings written as the web's settings
  panel does (the base currency while the Pot holds no money entry — a Pot without settings gets one this way —, its own
  categories added and renamed) through core's sealed-meta write (`session/NodeMetaWrite.kt`, the web's
  `writeSealedMeta`: only an absent blob is fresh, a `409 stale_revision` re-runs only the writer's own change on what the
  server holds; `NodeMetaWriteTest`). A currency's minor units are the platform's (`java.util.Currency`,
  `NumberFormatter`) where the web asks `Intl`; the Pot stores them, so a disagreement is never read twice differently.
  A Pot is created from Expenses' list (at the root of a space the member picks; a folder's "New" menu is Home's, not
  built) through core's node create (`session/NodeCreate.kt`, the web's `createContentNode`: a fresh key wrapped under the
  parent's, the name and the blinded slug token sealed under it, bound to the id the client mints), its token input
  folded as the web folds it (`crypto/Naming.kt`, held to `v1.json#name_folding` and `#slug_token` on both primitives; a
  Pot the web created collides with the app's of the same name, measured live by `PotLiveTest`). `core/…/expenses` ports the web's domain (the revision codec and
  its pad, the v1 format, the exact arithmetic on an integer type of its own, `Big`, held to `java.math.BigInteger`,
  the ledger, the heads), held to `contracts/expenses/v1-vectors.json` and the rules the vectors do not reach
  (`ExpensesVectorsTest`, `LedgerRulesTest`, each rule killed by a mutation); the web and the app read and write the
  same Pot to the cent (measured 2026-11-08, `PotLiveTest` beside the web's own page). Every write takes the web's path:
  a batch sealed on what is held under the client's rules (`expenses/PotWrites.kt`, the web's `sealPotWrites` and
  `eraseParticipant`; `PotWritesTest`), sent at the Pot's epoch through core's `session/NodeEpochWrite.kt` (the device
  floor, `node_rekey_pending`, `stale_epoch`; `NodeEpochWriteTest`), and every read checked for a revision dropped or
  altered (`expenses/LedgerCheck.kt`, the web's `checkLedger`, its notice above the Pot; a live Pot checks complete). This
  app drives no re-key, so where the web's member pulls a Pot's path forward (ADR 0111 decision 11) it waits, as the web's
  guest does; and it re-opens no scope rotated after the tenant was read, so a Pot re-keyed past that read is not found
  again and the write is refused until the app reads the tenant anew. An entry's receipts are added, opened and taken off
  as the web's editor does (`expenses/Receipts.kt`, the web's `receipts.ts`: images and PDFs up to 10 MiB, 100 an entry,
  a receipt the save no longer names dropped; `ReceiptsTest`), each one an application blob of the Pot through core's
  `blob/` package (the web's `applicationBlobs.ts`, ADR 0112): its key wrapped under the Pot's, its bytes sealed in
  frames (`v1.json#chunk_frame`, `#chunk_frame_size`, `#file_blob` on both primitives), its name and type in a padded
  `blob-meta` seal, uploaded before the entry that names it is written — a full space's quota skips the receipt and
  saves the entry. What a receipt is, its bytes decide when it is opened (`blob/Sniff.kt`), never the type it was
  stored under; a PDF is only drawn (Android's `PdfRenderer`, which reads a file, through one in the app's cache deleted
  after the drawing; PDFKit from memory). The object store's presigned URLs are another host: they are sent through
  `VeyqAccount.outside`, never with the account's bearer. The web opens a receipt the app uploaded (measured 2026-11-08).
- **Not built yet:** every other write (another kind's node), the
  other applications' views behind the bar, a CI job for the apps. The grant check is held by `GrantTrustTest` against a server the test plays — each refusal killed by
  a mutation of the rule it pins, but for three a second rule also holds (a pending or self-naming signer, and a cycle
  of signers, end unanchored through the signer's own judgment) — and by `v1.json#key_chain`, `#identity_pin`,
  `#scope_succession`, `#invite_key`, `#join_record`, `#join_endorsement`, `#value_key`, `#slug_token` and `#name_folding` on both primitives. `src/mobile/` verifies its dependencies as `src/backend/` does
  (`gradle/verification-metadata.xml`, held by `scripts/validate_build_input_pins.py`): a new dependency or target
  owes a `./gradlew --write-verification-metadata sha256` run over the tasks that resolve it.
- Two implementations of the suite now exist. A change to the suite changes the vectors first, and both the web's
  package and `core` must meet them; `src/mobile/`'s `./gradlew :core:jvmTest :core:macosArm64Test` is the app's half
  of that proof — the same `Conformance` over BouncyCastle and over libsodium.
- **No ready-made Kotlin Multiplatform library covers the Apple side** (checked 2026-11-08): cryptography-kotlin 0.6.0
  has neither ML-KEM nor Argon2id (Argon2 is an open issue there); the libsodium bindings published for Kotlin
  Multiplatform (0.9.5) ship a libsodium from before 1.0.22 and so no ML-KEM. Should one of them cover the suite's
  primitives, it replaces the build script, and the conformance suite says whether it may.

## Alternatives considered

- **A shared UI (Compose Multiplatform).** Rejected: the owner wants each platform's own UI (ADR 0122 relies on the
  platform's own navigation, the iOS search tab among it).
- **The Apple primitives in Swift on CryptoKit.** Rejected: CryptoKit has no Argon2id, its Ed25519 signatures are not
  deterministic, and its primitives sit outside Kotlin, so the conformance suite could not run on them as it runs on
  the JVM.
- **Argon2id ported to Kotlin by hand.** Rejected while a maintained, vendor-neutral library provides it: a port is
  crypto code nobody else reviews.
- **Hand-written DTOs.** Not open: the contracts are the source of truth (root `CLAUDE.md`).

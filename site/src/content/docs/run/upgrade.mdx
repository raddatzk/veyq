The schema migrates at boot with no operator gate and the migration set carries no downgrade path, so the backup
is not a precaution taken *around* this procedure — it **is** the way back ([ADR 0056](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0056-instance-durable-state-and-cold-logical-backup.md) §6).
Everything else below exists to keep that backup usable: to name the release you are leaving, and to notice a
recipe change before it becomes a failed `up`.

**Which of these steps has ever been executed.** Step 2 is rehearsed on every `scripts/run_web_e2e.py` run: it
captures a live instance, destroys it, restores it and runs a suite against the result, and it holds the production
capture to resolving the production project instead of whatever happens to run out of `infra/`. The DATA half of the
whole upgrade is rehearsed by the upgrade proof below, from jars rather than images. **No image has ever been
published**, so no other step here has ever run — not the stop, not the pull, not the recipe diff, not the rollback.
This is a procedure derived from the decisions that govern it, not from a rehearsal, and you are the one finding out
where it is wrong. Read it that way.

**The upgrade proof — what it covers, and what it does not** ([ADR 0057](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0057-release-identity-and-deployment-recipe.md) Decision 7).
`python3 scripts/run_web_e2e.py --upgrade` builds the **predecessor** in a worktree of its ref (its own fast-jar, its
own web dependencies and client) and lets its own e2e seeder seal content of every application into a fresh instance;
step 2's capture takes it, the restore puts it onto an instance freshly installed by **this** checkout's jar ("restore,
start", ADR 0056 §7), the candidate migrates it up at its start, must report `configSecretState: OK` (step 7), and this
checkout's reader opens every item the seeder recorded — names, date and place, the cover, every photo and file byte
for byte, the drop box's guest files, and a READ link as its guest sees it. The predecessor is the commit before the
one under test until the first release, the last release (`v<major>.<minor>`) from then on; `--upgrade-from <ref>`
names another one, and a ref older than the seeder is refused. The run's summary ends with the predecessor, both
builds' highest migration, the migrations changed or removed between them, and the outcome with its cause — a Flyway
refusal (a changed baseline's checksum above all) is named as such. Before the first release a red proof informs and
gates nothing; `container.yml`'s `upgrade-proof` job, which `publish` needs, is disabled until then
([backend/CLAUDE.md](https://github.com/raddatzk/veyq/blob/main/backend/CLAUDE.md) § Migrations). **What it does not cover:** it boots jars, not the published
images, so the pull, the recipe diff and the `up` of steps 4–6 and the rollback stay unrehearsed; and it says nothing
about the chart — `helm upgrade` from the predecessor's chart to the candidate's runs in no cluster; its immutable
fields and claims are compared on rendered manifests by `scripts/chart_upgrade_check.py` ([Upgrade](/veyq/run/upgrade/), Kubernetes), and a cluster leg is inbox #430.

<Tabs syncKey="target">
  <TabItem label="Docker Compose">

1. **Stop the application — and only the application.** *Cold* means the **writer** is stopped; MariaDB and
   Garage stay up, because the capture reads through their own interfaces (ADR 0056 §2).

   ```sh
   docker compose -f infra/docker-compose.prod.yml stop app
   ```

   **`scripts/instance_backup.py` does not check this, and does not pretend to** — it cannot know what "the
   app" is on your host. It is the one precondition you own, and the entire consistency argument rests on it:
   with the app down the database gains no rows, so a row whose object was never captured is impossible and
   there is no ordering to get right.

2. **Capture, then check the capture,** exactly as [Backup and restore § Capture](/veyq/run/backup-and-restore/#capture)
   shows for the production recipe: as root, on the `veyq_edge` network, with leg (c) read from the
   `veyq-config-secret` volume and copied to a medium of its own. The application is already stopped (step 1), so
   skip that page's first step and do not start it again at its last.

   Do not skip `verify`. A capture that silently missed objects and one that is complete look identical until
   the day you need it, which is the day you find out. Encrypt it before it leaves this host ([Capture](/veyq/run/backup-and-restore/#capture)).

3. **Confirm the backup can name the release you are leaving.** Read `app.version` in the capture's
   `manifest.json`. A release is `<major>.<minor>`, and a release onto an existing tag **fails** rather than
   replacing it ([ADR 0057](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0057-release-identity-and-deployment-recipe.md)), so that tag
   names one fixed set of bits for good — which is what makes it a rollback target rather than a label. A
   `<major>.<minor>-SNAPSHOT` is not: its tag moves, so roll back to the digest you pinned instead. If the
   manifest records no release, the backup is still valid and still restorable; what it cannot tell you is which
   image to start it under, so write that down yourself now, from the admin console's **Server → Release**, while the
   instance you are leaving still exists to be asked. And keep a copy of `infra/.env`'s `VEYQ_IMAGE` and
   `VEYQ_ADMIN_IMAGE` lines: they name, by the digest you verified when you installed them, the pair you roll
   back to.

4. **Verify the new release and pull both of its images**, so the download is not part of the outage: run
   [Verify a release](/veyq/run/verify-a-release/) with `version=<new-version>`. It pulls the app and the admin image by digest, extracts
   the new recipe into `./recipe-<new-version>/` and prints the two image lines step 6 pins. If either
   `cosign verify` fails, stop here — nothing has changed yet.

5. **Diff the new image's recipe against the one you are running.** The image's copy is authoritative for the
   version it belongs to (ADR 0057), and a version that adds a service or a required variable has **no other
   delivery path to you** — the first sign of one you missed is a `up` that dies on a missing variable.

   ```sh
   diff -u infra/docker-compose.prod.yml ./recipe-<new-version>/docker-compose.prod.yml
   diff -u infra/.env.example            ./recipe-<new-version>/.env.example
   ```

6. **Apply what the diff showed, then bring the new version up.** Take the new recipe as yours
   (`cp ./recipe-<new-version>/docker-compose.prod.yml ./recipe-<new-version>/.env.example infra/`), carry any
   new variable into `infra/.env`, replace its `VEYQ_IMAGE` and `VEYQ_ADMIN_IMAGE` lines with the two step 4
   printed — both, never one — and:

   ```sh
   docker compose -f infra/docker-compose.prod.yml up -d
   ```

   The schema migrates during this boot. There is no gate and no prompt.

7. **Verify, and not by "it started".** Read the instance's config-secret state as the Server Owner
   (`GET /api/tenants/{id}/mail-settings` → `configSecretState: OK`), then have a person sign in and **open a
   Memory that contains media**. That is the one assertion touching all three legs at once — the row, the
   object and the key are three different failures wearing the same "it looked fine".

  <TabItem label="Kubernetes">

The same procedure as under Docker Compose, with the same reason it is a procedure: the schema
migrates at boot with no gate and no downgrade path, so the backup is the way back. Two things are specific
to this target.

- **One app pod, `strategy: Recreate`, and that is not a tuning knob.** Kubernetes' default `RollingUpdate`
  starts the new pod before the old one stops, which would run two migrators against one schema during every
  upgrade; `Recreate` is what makes "one migrator at a time" true, at the cost of a short outage per upgrade.
  The day the update mechanism is decided (inbox #121) this is the constraint to revisit.
- **What the chart change between two releases is checked for — and what not** ([ADR 0064](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0064-kubernetes-helm-deployment-target.md)
  § Decision, the chart-upgrade check). `python3 scripts/chart_upgrade_check.py` reads the upgrade proof's predecessor's `charts/veyq` out of git
  (the commit before until the first release, the last `v<major>.<minor>` from then on; `--upgrade-from <ref>` names
  another), renders it and this checkout's chart with each of this chart's `ci/` values files, and refuses what
  `helm upgrade` cannot apply or would lose data over: a Deployment's or StatefulSet's `selector`, any StatefulSet
  `spec` field the API server does not let an update change (all but `replicas`, `ordinals`, `template`,
  `updateStrategy`, `persistentVolumeClaimRetentionPolicy`, `minReadySeconds`) - `serviceName`, `podManagementPolicy`,
  the claim templates whole (name, order, access modes, class, size, their labels), a claim's access modes,
  class or a shrinking size, a RoleBinding's `roleRef`, a kind changed under a name, a StatefulSet or claim gone. It
  also renders this chart with the predecessor's `ci/` values: values you already run must still pass the schema.
  `container.yml`'s `test` job runs it; before the first release its findings inform, from it they fail the build.
  **It renders and installs nothing**, so it does not see a missing StorageClass or one that cannot expand a growing
  claim, admission, image pulls, your data surviving the upgrade, a `mariadbPassword` changed on upgrade (MariaDB keeps
  the old one), a value path no `ci/` file
  sets, or what you edited in the cluster by hand. A cluster leg that would is inbox #430.
- **Kubernetes-native backup is not built** ([ADR 0064](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0064-kubernetes-helm-deployment-target.md)
  defers it, [ADR 0056](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0056-instance-durable-state-and-cold-logical-backup.md)'s gap
  statement stays accurate). Until it is, [Backup and restore](/veyq/run/backup-and-restore/)'s capture runs against this cluster through
  `kubectl port-forward` to MariaDB and Garage and `kubectl cp` of the key file, with the app **scaled to
  zero** for the duration (`kubectl -n veyq scale deploy/veyq-app --replicas=0`) — *cold* means the writer is
  stopped, and that is the precondition you own. The key is copied out before the scale-down, because only the
  app pod mounts its claim, and the capture then puts it on a medium of its own, never in the capture directory
  ([Capture](/veyq/run/backup-and-restore/#capture)).

```sh
# 0. leg (c) out of the pod first, while it still mounts the claim, to a file only you can read
(umask 077; kubectl -n veyq cp "$(kubectl -n veyq get pod -l app.kubernetes.io/component=app \
  -o jsonpath='{.items[0].metadata.name}')":/var/lib/veyq/config-secret.key ./veyq-config-secret.key)
kubectl -n veyq scale deploy/veyq-app --replicas=0      # 1. stop the application, and only it
# 2. capture and verify — Backup and restore, through port-forwards, with
#    --config-secret-file ./veyq-config-secret.key --key-into /media/usb-stick/veyq-<stamp>.key;
#    then delete ./veyq-config-secret.key — the key now lives on its own medium, never in the capture
helm upgrade veyq "oci://ghcr.io/raddatzk/charts/veyq@${chart_digest}" -n veyq -f my-values.yaml \
  --set image.digest="${app_digest}" --set admin.image.digest="${admin_digest}"   # Verify a release, <new>
# 3. the schema migrates during this boot; then verify as the compose runbook says — not by "it started"
```

The new chart names the new release as both images' tag; pin each image to the digest the verification resolved
for it: they ship as one release, and only one of a mismatched pair migrated the schema. With a digest set the pod
runs `repository:tag@digest`, and the node pulls by the digest. Rollback is the backup plus the previous chart's
and images' digests, exactly as under compose.

## Rollback

**Rollback is the backup plus the tag, and both are nameable only because a release is immutable.** Install the
release you left first: a freshly installed instance on the two lines step 3 kept (`VEYQ_IMAGE` and
`VEYQ_ADMIN_IMAGE` pinned back, the app started once and stopped, as [Restore](/veyq/run/backup-and-restore/#restore--onto-a-freshly-installed-instance) requires), then restore the capture
from step 2 onto it. The order is the rollback: restored onto the new release, the same capture is accepted as an
older backup and migrated up again at the next start, which repeats the failed upgrade instead of undoing it —
the restore says so when it sees one. There is no other way back: the migrations carry no down path, so an instance
that has booted on the new schema cannot be handed to the old image.

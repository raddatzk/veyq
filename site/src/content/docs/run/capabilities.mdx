A capability is a switch over what this instance offers at all: public links, groups, devices that unlock without the
Secret Key. You decide it for every tenant and every member, and a tenant owner can switch some of them off further for
their own tenant
([ADR 0088](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0088-the-capability-register-is-a-tree-switched-by-operator-and-tenant.md)).

## What a capability is

**It is not a permission.** Who may do what in a space is decided inside the space, by its owner and its members'
roles, not by you. A capability decides whether the thing is offered to anyone. When one is off, the instance leaves
its id out of the list it publishes before sign-in (`GET /api/setup`), so the web client hides the feature, and the
server refuses the action with `422 capability_disabled`, so a client that ignores the list is refused all the same.

**The entries form a tree.** An id is a dotted path under a root: `core` for the platform, and an application's own
name (`memories`, `depot`), which is an entry itself: the switch of that application as a whole. An entry is active only when it and every entry above it are on: the server ANDs along the
path, and no client works it out itself. Switching a parent off therefore switches its children off. A child keeps
its own switch while that happens: a child you switched off yourself stays off when its parent comes back on, and a
child you left on comes back with it.

**There are two levels.** You switch for the whole instance. A tenant owner switches for their own tenant as well, in
the tenant settings of the web client (**Settings → Capabilities**), and can only narrow what you allow, never widen it:
an entry is on in a tenant only when it is on for you and for them, along the whole path. Which entries a tenant owner
may switch is the catalog's `levels`, marked below and in the console. Entries the web client offers on the sign-in
screen (remembered devices, unlocking without a password, adding a device from another one) are yours alone, because
the sign-in screen reads your list before any tenant is known. The list before sign-in (`GET /api/setup`) is your level;
after sign-in each member's client reads their tenant's (`GET /api/tenants/{tenantId}/capabilities`), and the gates
refuse per tenant.

**Switching off never deletes stored data.** What a switch does to what already exists is
[below](#what-acts-at-once-and-what-only-on-new-data).

## Switch an entry

In the admin console, **Server → Capabilities** shows the entries as a tree. Each entry shows its title, what it is
for, and its state: **On**, **Off**, or **Off through** the parent that is off. **Switch off** first shows what
that does to new and to existing data, in the entry's own words, and asks you to confirm. **Switch on** asks nothing.

The CLI does the same
([how to run it and sign in](/veyq/run/first-run/#the-veyq-admin-cli)):

```sh
docker compose -f "releases/<release>/docker-compose.prod.yml" --env-file .env exec \
  -e VEYQ_ADMIN_EMAIL=you@example.com -e VEYQ_ADMIN_PASSWORD \
  admin veyq-admin capabilities list
```

| Command | What it does |
|---|---|
| `capabilities list` | Print the tree: each id indented by its depth, its state (`on`, `off`, or `off through <id>` naming the nearest ancestor that is off), its title, and what it is for |
| `capabilities off <id>` | Switch the entry off, then print what that does to new and to existing data |
| `capabilities on <id>` | Switch the entry back on. Under a parent that is still off, it stays off until the parent is on |

All three print text, not JSON. `--lang en` or `--lang de` picks the language of the entries' text. Without it the
CLI reads `LC_ALL`, then `LANG`, inside the container: German when the value starts with `de`, English otherwise.
An id the instance does not know is refused (`capability_not_found`, exit `1`), and nothing is stored.

A switch is stored in the database, so a database backup carries it. It acts on the next request, without a restart:
the application reads the switches through an in-process cache that each write clears, which holds for the single
replica both recipes run.

## External services

Three entries are outside services a member's browser calls directly, never through your server: the map tiles
(`memories.map`), the geocoder that names places (`memories.places`) and the breached-password check
(`core.breached-password`). Their addresses are yours to set, in **Server → External services** or with the CLI:

```sh
veyq-admin services list
veyq-admin services set memories.map --url 'https://tiles.example.com/{z}/{x}/{y}.png' --attribution '© Example'
veyq-admin services set memories.places --url https://geocoder.example.com
veyq-admin services unset core.breached-password
```

A new instance starts with OpenStreetMap's tiles, Nominatim and the Have I Been Pwned range API. A service is used only
while it has an address **and** its entry is on: the members' clients read the address from the capabilities, and the
Content Security Policy the server sends allows the service's origin only then, so a browser refuses any other. An
instance without internet runs with all three unset (or switched off): no map, place names typed by hand, no check of
new passwords against known leaks. Map tiles take a `{z}/{x}/{y}` template and the attribution your provider asks
for; the geocoder takes a Nominatim-compatible base address; the breach check the prefix the first five characters of
a hash are appended to. A tenant owner may switch the maps and place names off for their own space; the policy follows
your level only. The admin console's own first-run screen reaches only the default breach-check address.

## Requirements

A requirement tightens an entry instead of switching it off
([ADR 0088](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0088-the-capability-register-is-a-tree-switched-by-operator-and-tenant.md)
decision 8). In the console each entry lists its requirements with **Require** and **Clear**; a requirement of days takes
a number from 1 to 3650 first. Setting one shows what it does to what exists and asks you to confirm. The CLI:

```sh
veyq-admin capabilities require core.public-shares --requirement linkMaxDays --value 30
veyq-admin capabilities require core.public-shares --requirement linkPassword --value 1
veyq-admin capabilities require core.public-shares --requirement linkMaxDays --value off
```

`capabilities list` prints each entry's requirements with their value. A tenant owner can set the requirements of the
entries they may switch for their own tenant; the value in effect is the stricter one (a flag set at either level, the
smaller number of days), so a tenant tightens yours and never loosens it. Every member's client reads the values with
the capability, before sign-in yours, after it the tenant's.

A requirement acts at once, on what exists too: a link that misses one answers its guests like an unknown link until
its owner fixes it or you clear the requirement; nothing is written onto it. The members' list of links marks such a
link and names why, a switch included, so nobody has to try a link to find out. `passwordMaxDays` is yours alone, like the
remembered-device switches, and counts from a session's sign-in, or from the moment a device was added from another
one: switch `core.device-linking` off if a device must never get a session without the password.

## What acts at once, and what only on new data

The rule ([ADR 0088](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0088-the-capability-register-is-a-tree-switched-by-operator-and-tenant.md)
decision 5) is that a switch whose purpose an existing thing would defeat acts on that thing too, and any other
switch refuses only what is new.

- **Device switches act at once.** With `core.remember-device` off the server leaves every remembered device's key
  out of what it hands a member at sign-in; with `core.remember-device.passwordless` off, every password-less
  device's. It deletes neither. A member on such a device then needs the password **and** the Secret Key from the
  Emergency Kit, and the sign-in screen says why. The password with the Secret Key always works, so nobody is locked
  out, and switching back on lets every device unlock as before. Tell your members before you switch one off.
  `core.device-linking` off also stops an addition that is under way; devices added before are not affected.
- **Share switches act at once, on existing links too.** With a share switch off, no link of its kind can be made,
  renewed or switched back on, and every link of its kind that already exists stops working: a guest sees the same
  "This link isn't available" page as for an expired link, and nothing tells them the instance switched it off.
  `core.public-shares` stops every kind, its two children only their own. Nothing is deleted, so switching back on
  brings every link back as it was. A download or upload address the server signed just before stays usable until it
  expires, ten minutes by default, as after a member turns a link off.
- **An application switch acts at once, and makes the application read-only.** With `memories` or `depot` off,
  nothing of that application can be added or changed: no new Memory or file, no upload, rename, move, cover or new
  link, and a guest's upload through a link that exists is refused. Everything in it still opens and downloads, for
  members and through the links that exist, and members can still delete to the trash and restore. A rotation of keys
  and a moderation measure still reach it. Every member of the tenant sees a banner saying the application is switched
  off here, so they have time to save what they want to keep. The application's own entries below it
  (`memories.places`, `memories.map`) are off with it. Nothing is deleted: switched back on, everything is as before.
- **Feature switches refuse only what is new.** With `core.group-space` off no group can be created, and every
  existing group stays fully usable.

The off states are covered by tests; they have not yet been checked in a real browser
against a switched instance.

## Designed, not built

None of the following exists yet. It is the design in ADR 0088, not a promise of what comes next or when. Each entry
names what the server would see in order to refuse it: a switch exists only where it can.

**Core entries the catalog does not hold yet.**

| Entry | What the server would see |
|---|---|
| `core.personal-space` | the personal scope; off means no new content in it, while the scope itself (keys, favorites) stays |
| `core.member-invites` | the member-invite endpoint |
| `core.self-registration` (idea) | a new sign-up endpoint, off by default |
| `core.push` (native apps) | the push services' wake-up, which carries no content |

**Memories.**

| Entry | What the server would see |
|---|---|
| `memories.chapters` | the Chapter node kind |
| `memories.journal` (planned) | a node kind or blob role the server would then see |
| `memories.gpx` (planned) | a blob role for tracks: the server would learn *that* a Memory has a track, never where |
| `memories.faces` (idea) | a role for the face index, which is biometric data |
| `memories.public-shares`, `.contribute`, `.drop-box` | inherit from `core.public-shares`, so core switches every application's links off at once |
| `memories.public-shares.download-originals` | the original file's blob role. Waits on a measurement: if guests stream video from the original, this switch would also stop their video playback |

**Depot.** Its own `public-shares`, `.contribute` and `.drop-box` would inherit from core, and its drop box would also
gate creating a drop box, which `core.public-shares.drop-box` does for the whole instance today.

**Beyond the entries.**

- **Two more requirements**: sharing only with verified identities (not buildable as specified: there is no verified
  identity the server could check), and keeping no decrypted data on a native device (only the app could keep it, the
  server cannot enforce it).
- **Configuration as code** (inbox #444): declaring switches in the compose file or the Helm values instead of
  switching them in the console.

## Not switches

- **Export and import** cannot be switched off, because no switch could be enforced: whoever can read something
  holds it in plain text on their own device.
- **Mail, the object store and ACME** are preconditions of an instance, not features of it.
- **Quotas and limits** (a tenant's storage quota, the per-link storage limit, a file-size cap, retention periods)
  are parameters, set where they are described, not switched.
- **Never switchable:** derivatives, recovery (without it a forgotten password and a lost Emergency Kit lose the
  data), the trash and the other basics of a space.

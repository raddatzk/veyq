## Install

<Tabs syncKey="target">
  <TabItem label="Docker Compose">

`veyqctl` installs the instance from a release ([ADR 0096](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0096-veyqctl-manages-an-instance-from-immutable-releases.md)):
the app, its administration surface, MariaDB, Garage, and a Traefik that terminates TLS in front of them. Fetch and
verify `veyqctl` first ([Verify a release](/veyq/run/verify-a-release/#veyqctl-the-first-time)), then:

```sh
cd /opt/veyq
./veyqctl install --set VEYQ_RELEASE=<major> \
  --set VEYQ_DOMAIN=veyq.example.org --set VEYQ_ACME_EMAIL=you@example.org
```

`VEYQ_RELEASE` is the release line the instance stays on: a major (`1`, its newest release), an exact release
(`1.4`, pinned) or `latest` (the default); [Upgrade](/veyq/run/upgrade/#which-release-upgrade-takes) says what each
means later. A value you do not pass is asked for at a terminal, and refused by name without one. An optional
variable ([Configuration](/veyq/run/configuration/)) is passed the same way, `--set ADMIN_DOMAIN=…`.

`install` refuses a home that already holds an instance, and then, in order:

1. **Resolves the release** `VEYQ_RELEASE` selects among the GitHub Releases of `raddatzk/veyq`, never a prerelease or
   a snapshot. `--source <directory or URL>` reads a mirror in the same layout instead, verified exactly the same way.
2. **Verifies the release's `manifest.json`** against its signature, then **both images** by the digests it names,
   before anything is pulled, and
   **fetches the release's files** into `releases/<release>/`, each checked against its sha256 — both exactly as
   [Verify a release](/veyq/run/verify-a-release/) shows by hand.
3. **Writes `.env`** (mode `0600`) from the release's template, `env.example`: the four secrets generated, the two
   image lines from the manifest, your values filled in. Every secret is required and has no default in the recipe,
   so an `up` with one missing fails with its name instead of starting on a password printed in this repository.
4. **Brings the stack up** and waits until every service is healthy:
   `docker compose -f releases/<release>/docker-compose.prod.yml --env-file .env up -d --wait`, plus
   `-f compose.override.yml` when that file exists. It ends by naming the admin console's address.

The instance lives in `/opt/veyq` (`--home` names another):

| Path | What it is |
|---|---|
| `.env` | The instance's values, `0600` |
| `compose.override.yml` | Optional, yours: a Compose overlay laid over the recipe on every command (a port, a network, a CA), kept across upgrades |
| `state.json` | The running release, the Compose project, the source |
| `releases/<release>/` | That release's files, as published; an upgrade adds the next one beside it |
| `backups/` | The captures `backup` and `upgrade` take: the database and the store's index each |

No directory here holds an object pool: it lives where `.env`'s `VEYQ_BACKUP_OBJECTS_TO` names — by intent another disk
or another store, since a pool on the store's own disk dies with it ([Backup and restore](/veyq/run/backup-and-restore/#capture)).

`start`, `stop`, `status` and `logs [-f] [service]` address the stack by its project; `status` exits non-zero unless
every service is healthy.

**By hand**, without `veyqctl`: verify the release and fetch its files into `releases/<release>/` as
[Verify a release](/veyq/run/verify-a-release/) shows, then

```sh
cd /opt/veyq
(umask 077; cp "releases/${release}/env.example" .env)    # fill in every value; the two image lines are the manifest's
docker compose -f "releases/${release}/docker-compose.prod.yml" --env-file .env up -d --wait
```

The recipe names its project (`name: veyq`), so nothing else has to be passed. An instance set up by hand has no
`state.json`, so `veyqctl` does not manage it; run it by hand from then on, as each page here shows.

**Every container runs unprivileged, and the proxy cannot reach the database**
([ADR 0071](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0071-runtime-hardening-on-both-targets.md)). Each service drops every capability,
cannot escalate, runs as a non-root user and has a read-only root. A one-shot `volume-ownership` service chowns the
Garage and ACME volumes to their writers first, so `ps` lists it as exited (0) after every `up`, and that is its
done state. Three networks separate the peers: `veyq_edge` (Traefik, app, Garage), `veyq_db` (app, MariaDB, no
route out) and `veyq_admin` (app, admin container, and Traefik for the `ADMIN_DOMAIN` router). A command that joins
the stack names one of them.

`infra/kubernetes/charts/veyq` is the second deployment target ([ADR 0064](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0064-kubernetes-helm-deployment-target.md)):
the same four workloads as the production compose file — the app, its administration surface, MariaDB and
Garage — on an operator's own cluster, with a Gateway API implementation of the operator's choice in place of the
compose file's Traefik (the chart owns one `Gateway`; the implementation, its CRDs at v1.5 or later and, for the ACME
opt-in, cert-manager are yours to install first). It deploys published
images and builds nothing; it **generates nothing** either, so every secret is yours to supply and an install
that leaves one unset is refused by name (`values.schema.json`). One release per namespace: the app projects
tenant domains as `HTTPRoute`s (and `ListenerSet`s) into its own namespace and lists them by label, so two releases there
would reconcile each other's routing away.

```sh
# Verify a release first: it leaves ${release}, ${app_digest}, ${admin_digest}, ${tools_digest} and ${chart_digest}
chart="oci://ghcr.io/raddatzk/charts/veyq@${chart_digest}"
helm show values "$chart" > my-values.yaml        # fill in: domain, storeDomain, every key under secrets,
                                                  # gateway.className, the gateway.tls block,
                                                  # backup.existingClaim — a PersistentVolumeClaim you created
                                                  # for the backup gate (or backup.enabled: false), and
                                                  # networkPolicy.ingressFrom — your gateway's data-plane
                                                  # pods; for Traefik in the `traefik` namespace, e.g.:
#   gateway:
#     className: traefik
#   networkPolicy:
#     ingressFrom:
#       - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: traefik}}
#         podSelector: {matchLabels: {app.kubernetes.io/name: traefik}}
helm install veyq "$chart" -n veyq --create-namespace -f my-values.yaml \
  --set image.digest="${app_digest}" --set admin.image.digest="${admin_digest}" \
  --set backup.image.digest="${tools_digest}"
```

The published chart already names the release: its `appVersion` is the image tag the images default to, and
the image repositories default to the upstream's. Pin the three digests the verification resolved, so the pods run
exactly what you verified. Helm finds a veyq chart **only by its digest or its exact version** (`--version 1.4`):
the version has two parts, and Helm's tag listing skips every tag that is not three-part SemVer, so `helm install`
without a version, or with a range, finds nothing (measured with Helm 4.0.1, ADR 0064).

**From a checkout** the chart is `./charts/veyq`, and its in-tree version is a placeholder (`0.0-dev`) no publish
uses, so name the release yourself: add `--set image.tag="${release}" --set admin.image.tag="${release}"` to the
same `helm install`, with `./charts/veyq` in place of `"$chart"`.

The rest of what is specific to this target is on [Kubernetes](/veyq/run/kubernetes/).

## Worth knowing

The admin surface's two exposure modes and the `veyq-admin` CLI are on
[First-run setup and the admin console](/veyq/run/first-run/).

Routing, certificates and HSTS are on [Networking and TLS](/veyq/run/networking/); the config-secret volume
and why it must persist are on [Storage and email](/veyq/run/storage-and-email/#the-config-secret-key).

- **Upgrading is a procedure, not a flag change.** It has its own section — [Upgrade](/veyq/run/upgrade/) — and
  the reason it is not one line is that the schema migrates at boot with no gate and no downgrade path.
- **There are two images per release, and they are pinned together.** `VEYQ_IMAGE` and `VEYQ_ADMIN_IMAGE` are
  built, versioned and cosign-signed by the same publish ([ADR 0057](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0057-release-identity-and-deployment-recipe.md)),
  and one release's manifest names both by digest, which is where `veyqctl` writes them from. A mismatched pair is two
  versions of one instance, and only one of them migrated the schema.
- **The recipe is the release's files.** The compose file, its `.env` template and `garage.toml` are assets of an
  immutable GitHub Release, beside the manifest that names the images it was published with, so the recipe you run a
  release with cannot drift from the images it describes, and nothing in a published release can change
  ([ADR 0096](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0096-veyqctl-manages-an-instance-from-immutable-releases.md)).
  No image carries a recipe, and no repository checkout is needed.

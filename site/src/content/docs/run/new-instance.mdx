## Install

<Tabs syncKey="target">
  <TabItem label="Docker Compose">

`infra/docker-compose.prod.yml` is the deployment artifact: the app, its administration surface, MariaDB,
Garage, and a Traefik that terminates TLS in front of them. It is **standalone**, not an override of the dev
file — that file has no app service at all, publishes `3306`/`19000`/`18080`, and ships `change-me` passwords.

```sh
# first: Verify a release — it leaves the recipe in ./recipe-<version>/ and prints two image lines
cp ./recipe-<version>/docker-compose.prod.yml ./recipe-<version>/.env.example infra/
cp infra/.env.example infra/.env          # then fill in every value (it is gitignored), and the two image lines
docker compose -f infra/docker-compose.prod.yml up -d
```

**Every secret is required and has no default.** A missing variable fails the `up` with the name of the variable,
rather than starting an instance on a password that is printed in this repository.

**Every container runs unprivileged, and the proxy cannot reach the database**
([ADR 0071](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0071-runtime-hardening-on-both-targets.md)). Each service drops every capability,
cannot escalate, runs as a non-root user and has a read-only root. A one-shot `volume-ownership` service chowns the
Garage and ACME volumes to their writers first, so `ps` lists it as exited (0) after every `up`, and that is its
done state. Three networks separate the peers: `veyq_edge` (Traefik, app, Garage), `veyq_db` (app, MariaDB, no
route out) and `veyq_admin` (app, admin container, and Traefik for the `ADMIN_DOMAIN` router). A command that joins
the stack names one of them.

  </TabItem>
  <TabItem label="Kubernetes">

`charts/veyq` is the second deployment target ([ADR 0064](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0064-kubernetes-helm-deployment-target.md)):
the same four workloads as the production compose file — the app, its administration surface, MariaDB and
Garage — on an operator's own cluster, with the ingress controller in place of the compose file's Traefik, and
the operator's choice. It deploys published
images and builds nothing; it **generates nothing** either, so every secret is yours to supply and an install
that leaves one unset is refused by name (`values.schema.json`). One release per namespace: the app projects
tenant domains as `Ingress` objects into its own namespace and lists them by label, so two releases there
would reconcile each other's routing away.

```sh
# Verify a release first: it leaves ${version}, ${app_digest}, ${admin_digest} and ${chart_digest}
chart="oci://ghcr.io/raddatzk/charts/veyq@${chart_digest}"
helm show values "$chart" > my-values.yaml        # fill in: domain, storeDomain, every key under secrets,
                                                  # the ingress.tls block, and networkPolicy.ingressFrom —
                                                  # your ingress controller's pods:
#   networkPolicy:
#     ingressFrom:
#       - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: ingress-nginx}}
#         podSelector: {matchLabels: {app.kubernetes.io/name: ingress-nginx}}
helm install veyq "$chart" -n veyq --create-namespace -f my-values.yaml \
  --set image.digest="${app_digest}" --set admin.image.digest="${admin_digest}"
```

The published chart already names the release: its `appVersion` is the image tag both images default to, and
the image repositories default to the upstream's. Pin the two digests the verification resolved, so the pods run
exactly what you verified. Helm finds a veyq chart **only by its digest or its exact version** (`--version 1.4`):
the version has two parts, and Helm's tag listing skips every tag that is not three-part SemVer, so `helm install`
without a version, or with a range, finds nothing (measured with Helm 4.0.1, ADR 0064).

**From a checkout** the chart is `./charts/veyq`, and its in-tree version is a placeholder (`0.0-dev`) no publish
uses, so name the release yourself: add `--set image.tag="${version}" --set admin.image.tag="${version}"` to the
same `helm install`, with `./charts/veyq` in place of `"$chart"`.

The rest of what is specific to this target is on [Kubernetes](/veyq/run/kubernetes/).

## Worth knowing

The admin surface's two exposure modes and the `veyq-admin` CLI are on
[First-run setup and the admin console](/veyq/run/first-run/).

Routing, certificates and HSTS are on [Networking and TLS](/veyq/run/networking/); the config-secret volume
and why it must persist are on [Storage and email](/veyq/run/storage-and-email/#the-config-secret-key).

- **Upgrading is a procedure, not a flag change.** It has its own section — [Upgrade](/veyq/run/upgrade/) — and
  the reason it is not one line is that the schema migrates at boot with no gate and no downgrade path.
- **There are two images per release, and they are pinned together.** `VEYQ_IMAGE` and `VEYQ_ADMIN_IMAGE` are
  built, versioned and cosign-signed by the same publish ([ADR 0057](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0057-release-identity-and-deployment-recipe.md)),
  so pin the same `<major>.<minor>` on both, each by the digest [Verify a release](/veyq/run/verify-a-release/) resolved. A mismatched pair is two versions of one instance, and only one of
  them migrated the schema.
- **The compose file and the env template ride inside the image.** Every published image carries the recipe it
  was built with at `/opt/veyq/deploy/`, so the file you deploy a version with cannot drift from the bits it
  describes, and it inherits the image's cosign signature instead of needing a second trust decision — which
  holds only for a recipe read out of the digest you verified, so [Verify a release](/veyq/run/verify-a-release/) extracts it from
  exactly that digest, never from a tag.

  (Note the current limit: the recipe is those two files, so the store's `garage.toml` still comes from this
  repository — the Helm chart carries its own copy as a `ConfigMap`, so the file has a second, self-sufficient
  home there, but the compose recipe still reads it from the repository's `infra/`. It used to be two files — ADR 0067 deleted
  `garage-init.sh` along with the image that ran it.)

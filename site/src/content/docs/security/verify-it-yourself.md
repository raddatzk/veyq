Every check below lives in the repository and can be run from a checkout. This page says what each one pins,
how to run it with the repository's own commands, and where it stops. None of them is a proof against an actively
malicious operator: that boundary is set by
[security-model § What holds today](https://github.com/raddatzk/veyq/blob/main/docs/crosscutting/security-model.md#what-holds-today-on-a-client-the-operator-does-not-serve),
and its rule applies here too: a check the server runs never closes a row of that table, because the operator
is the server.

:::caution[Nothing here has run in CI in this repository]
veyq was imported into a fresh repository on 2026-08-06 and has had no remote since
([ADR 0040](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0040-coverage-gaps-and-http-not-a-surface.md)),
so no workflow has executed in it. Two jobs have never run anywhere: `packages/crypto`'s and `admin-web`'s
`npm run check`
([architecture § 11](https://github.com/raddatzk/veyq/blob/main/docs/architecture/README.md#11-risks-and-technical-debt)).
No release has been built or published
([ADR 0057](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0057-release-identity-and-deployment-recipe.md)).
Everything on this page that is described as passing passes on a developer machine. The project's own rule is
that a test no CI run executes makes no coverage claim.
:::

## At a glance

| Check | What it pins | Where it runs |
|---|---|---|
| Crypto vectors + conformance tests | The bytes of suite v1 cannot move silently | `packages/crypto`, `web`, three backend tests |
| Mutation gate | The crypto tests' assertions are strong enough to kill every mutant | `packages/crypto`, `web` (StrykerJS) |
| Wire sweep | Sealed plaintext and capability tokens appear on none of six operator-readable surfaces | `scripts/run_web_e2e.py` (Docker, live backend) |
| Scope-access probe | Every operation answers a non-member, a proposal, a suspended tenant and a deleting group as the gate requires | backend, `OperatorBlindProbeTest` |
| Doc ↔ code guards | Every reference resolves; every contract field declares what the server may read | `scripts/validate_*.py` (buildless) |
| Release verification | The image you run is the one the publish workflow signed | [Verify a release](/veyq/run/verify-a-release/) |

## Reproducing the crypto vectors

[`contracts/crypto/vectors/v1.json`](https://github.com/raddatzk/veyq/blob/main/contracts/crypto/vectors/v1.json)
is the single source of truth for what suite v1 *is* on the wire. The implementation,
[`packages/crypto/src/v1.ts`](https://github.com/raddatzk/veyq/blob/main/packages/crypto/src/v1.ts), is held to it,
and every seal purpose has exactly one vector
([ADR 0017](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0017-crypto-primitives-and-post-quantum-strategy.md)
rule 4, [ADR 0072](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0072-a-seal-binds-its-object.md)
Decision 6). The order is fixed: a new primitive gets its vector first, and the implementation is made green
against it afterwards, never the reverse.

This page does not restate any byte format. Each vector group in the file carries a `note` that states its
encoding, and most notes also name how the group was generated. Several say they were generated by an
independent Python implementation, not by the suite under test. To reproduce a group, implement the encoding its
note describes and compare your bytes with the file.

The vectors for the hybrid post-quantum KEM are covered on [Cryptography](/veyq/security/cryptography/).

### Who asserts the file

| Stack | Tests | What they read |
|---|---|---|
| `packages/crypto` | `src/v1.conformance.test.ts` | The file's groups, every seal purpose among them. It also compares the file's seal purposes with the code's typed list in both directions, and checks that a seal refuses to open when one binding field or the purpose is changed |
| `web` | `argonParams.conformance.test.ts`, `trustDevice.conformance.test.ts`, `naming.conformance.test.ts` | The Argon2id profile web writes, the trust-device path, and the name foldings that are frozen into every slug token |
| backend | `SecretKeyProofTest`, `AuthAttestationTest`, `ChunkFramesTest` | The Secret-Key proof statements, the change-email attestation, the chunk-frame size |

**What this proves, and what it does not.** Only the TypeScript conformance test asserts the file's seals, so for
seals the vectors are a **single-implementation regression pin**. A refactor cannot silently move a suite's
bytes, but the file is not a cross-stack parity proof
([ADR 0017](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0017-crypto-primitives-and-post-quantum-strategy.md)
rule 4). The backend does no content crypto. It asserts the vectors only for the statements it rebuilds itself:
the Secret-Key proof and the change-email attestation. The cross-stack role is dormant until a second
independent implementation exists.

The file has **no tamper-rejection vectors**, and that is a decision. A rejection has no output to record, and the
GCM tag check that does the rejecting is the library's, outside any veyq test
([ADR 0045](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0045-mutation-testing-trust-chain-unit-layer.md)
Consequences).

## Running the conformance tests

The npm workspace is installed once, from the repository root. Then each package proves itself with its own
check (lint, typecheck, tests):

```sh
# from the repository root
npm ci

cd packages/crypto
npm run check
```

The web client's conformance tests run in its own check, from `web/`:

```sh
npm run check
```

The backend's tests run from `backend/`, on in-memory H2:

```sh
./gradlew check
```

`packages/crypto`'s `npm run check` has **never run in CI**. Its suites pass locally, and the use-cases they would
cover name them as `gaps`, not as coverage
([ADR 0040](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0040-coverage-gaps-and-http-not-a-surface.md)).
To keep that from leaving the profile unpinned, the Argon2id parameters web writes are also pinned against the
same vector by a web test on a job that a run did admit.

### The mutation gate

A test that runs proves only as much as its assertions pin. veyq measures that with mutation testing on the unit
layer: StrykerJS for the TypeScript crypto, and PIT for the backend's policy logic
([ADR 0045](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0045-mutation-testing-trust-chain-unit-layer.md)).
In `packages/crypto` the break threshold is **100, with no margin**: every equivalent mutant is disabled at its
own line with its measured reason, so a margin would buy only blindness. The reasoning lives in
[`stryker.config.mjs`](https://github.com/raddatzk/veyq/blob/main/packages/crypto/stryker.config.mjs).
From `packages/crypto/` (and again from `web/`, which has its own scope):

```sh
npm run mutation
```

Stryker mutates the source files **in place** and restores them on exit, so do nothing else in the tree while a
run is live. Mutation sees functional behaviour only. It cannot see timing, so a constant-time comparison is not
protected by it. It also raises trust in how *strong* an assertion is, not in whether the assertion is *right*
(ADR 0045 § Consequences). Its CI job, `mutation.yml`, has never run either.

## The wire sweep

The design sensor (ADR 0044, below) checks the contract. The wire sweep checks the **bytes the operator can
read** ([cc.security.wire-assertion](https://github.com/raddatzk/veyq/blob/main/docs/crosscutting/cc.security.wire-assertion.md),
[ADR 0053](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0053-wire-assertion-canary-sweep.md)).
The threat it closes is a **client regression**, not a hostile operator and not broken crypto: a value that
should have been sealed reaches an operator-readable surface in a build that passes every other check.

**The oracle is canary absence.** Each end-to-end suite unseals the server's own responses with the keys it
holds. Every string it recovers becomes a canary, so no canary is listed by hand and none can be forgotten.
After the suite runs, the orchestrator proves that none of those strings appears anywhere the operator could read
it. The proof is positive and narrow: *this plaintext, which the client sealed, appears nowhere on these
surfaces.* For the JSON bodies, where every field has a declared visibility, a second oracle applies. A field
declared opaque must not decode to readable text, and it must not be implausibly short: an AEAD value cannot be
under 28 bytes.

**Six surfaces are swept**, each for two needle sets:

| Surface | What is searched |
|---|---|
| Database | Every column of every table in the suite's own database (a data-only dump) |
| Object store | Object keys and stored object bytes |
| HTTP | Bodies, URLs and request/response headers as the client recorded them |
| Server log | Every boot log of the run and the log of every container in the stack |
| Statement log | Every SQL statement the database received during the run, including writes later undone |
| Mailbox | Every mail the run sent, decoded |

The second needle set is **every capability token the run handled**: each value the contract marks `token`
(bearer and refresh tokens, contributor, invite, recovery and pairing secrets, share-write proofs) and every
presigned URL. These are derived from the HTTP recording by that marker, never listed. The token sweep is armed by
its hashes: at least one token's SHA-256 must be found in the suite's database dump, or the suite fails.

The other sensors are armed by positive controls, never by a count of zero. Each boot log must name its database
and carry the shutdown line; the store's log must contain a key the run plants; the statement log must contain a
sentinel statement at each end of its window; the mailbox must contain a mail the run plants. The MariaDB, Traefik
and Mailpit container logs are swept without a control, so nothing proves they could show a leak. The S3 object
key's own guard, promised by ADR 0044, is **planned**, not built.

### How to run it

The sweep needs Docker and a built backend fast-jar. It brings up the bundled stack from
[`infra/docker-compose.yml`](https://github.com/raddatzk/veyq/blob/main/infra/docker-compose.yml) (MariaDB,
Garage, Traefik, Mailpit), gives each suite file its own database and a fresh backend boot, and sweeps after
each one. With the
workspace installed (`npm ci` above), build the jar first:

```sh
cd backend && ./gradlew quarkusBuild
```

A stale jar fails as a wrong answer, not as an error, so rebuild it after any backend change. Then, from the
repository root:

```sh
python3 scripts/run_web_e2e.py
```

With no arguments the orchestrator runs every `web/src/**/*.e2e.test.ts`. The run directory
`.e2e-out/<stamp>/` survives the run. It holds each boot log, each HTTP recording, each database dump the sweep
read, the statement log and every mail. These are throwaway credentials of throwaway instances, but they are raw
tokens all the same.

The parts that need no Docker run in the buildless trust chain. `validate_e2e_canaries.py` checks that every
suite contributes canaries, so the sweep cannot pass over an empty set. `validate_e2e_discovery.py` checks that
the orchestrator cannot report green after running nothing. `validate_wire_log_matcher.py` checks the needle
spellings and the controls.

### What a green sweep does not prove

The concern document keeps the full list. The ones a researcher should weigh:

- **Only values that were sealed.** A value the client never sealed is not a canary, so the sweep cannot see it.
  That case belongs to the field-visibility guard and the opacity check.
- **Only flows some suite drives.** Coverage is the residual gap, not correctness. Thin end-to-end coverage is
  tracked as open debt.
- **Only declared, textual HTTP.** A leak through an undeclared field, or through a response not marked as text,
  is outside the HTTP sensor.
- **The e2e topology, not the deployed one.** The reverse proxy carries no e2e traffic. The admin container's
  nginx log is trimmed rather than swept, and a cluster ingress keeps its own access log.
- **Only the encoders this stack uses.** A server that wrote a value in another spelling, such as upper-case hex
  escapes or base64, would not be matched.
- **The store keeps no history of object bytes.** An object uploaded and deleted inside one suite leaves its key in
  the swept request log, but its bytes nowhere the sweep reads.
- **Not tamper-proof.** The oracle sits outside the client, so a client cannot satisfy it by weakening an
  assertion. But a canary can be removed, and the removal is a visible diff. That is weaker than tamper-proof.

The sweep's enforcement is the `web-e2e` CI job. That job makes a coverage claim only once a CI run has executed
it, and this repository has run none since its import.

## The scope-access probe

[`OperatorBlindProbeTest`](https://github.com/raddatzk/veyq/blob/main/backend/src/test/kotlin/me/raddatz/veyq/core/http/OperatorBlindProbeTest.kt)
is, despite its name, **an authorization probe, not a blindness test**. It is the enforcement guard for the
scope-access gate
([uc.spaces.scope-access](https://github.com/raddatzk/veyq/blob/main/docs/features/spaces/use-cases/uc.spaces.scope-access.md),
[ADR 0042](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0042-http-failure-projection.md)).
It never looks at ciphertext. It checks who the server answers, and how.

The probe does not list the operations it covers. It derives them from the API interfaces generated from
`contracts/api/`, for core and every application. Each operation is then either probed or named on a reasoned
exclusion list, so an operation nobody classified fails on the day it is added. Each probe runs against fresh
fixtures with five personas:

1. **Stranger.** The real id and an invented id must get identical answers: the membership 404. Any difference is
   an existence oracle that would let a stranger enumerate ids. This is about guard order, which no static check
   can see.
2. **Unaccepted proposal.** Answered exactly as the stranger, because a proposal is not a membership.
3. **Member of a suspended tenant.** `403 tenant_suspended`, sent on a host no tenant claims, so the answer
   cannot come from the host filter.
4. **Member of a group being deleted.** A write gets `409 scope_deleting`; a read is not refused.
5. **Control.** The owner of an identical live group is refused by none of the above. Without this positive
   control, a probe that returned 404 for everything would satisfy the first two checks perfectly.

Every check anchors on `(status, code)`, never on "not 2xx".

**What it does not prove.** This is layer-1 access control, which the server enforces and the operator, being
the server, can skip. It protects one user from another against an honest server. It says nothing about what an
operator can read: that is the client's job, enforced with keys the server never holds
([security-model § The one guarantee](https://github.com/raddatzk/veyq/blob/main/docs/crosscutting/security-model.md#the-one-guarantee)).
It closes no row of § What holds today. It runs in the backend's root project, as part of `./gradlew check`
from `backend/`.

## Doc ↔ code guards

The doc-to-code validation layer is a set of buildless Python guards. The glob `scripts/validate_*.py` *is* the
registry: CI loops over it, so a new guard runs the moment it lands, and each guard's module docstring is its
documentation. CI runs them in `trust-chain.yml`, deliberately unfiltered so that a docs-only change is validated
too; the one exception is `validate_guard_gaps.py`, which tests the guards themselves and runs there when one of them
changes, and every night. The guards need `pyyaml`, which CI installs into a virtual environment. To run the chain locally, exactly as
CI does:

```sh
for f in scripts/validate_*.py; do python3 "$f"; done
```

**What a green chain means.** The coverage guard proves that every acceptance criterion has a test and that every
reference resolves. It cannot prove that the test proves anything. `assertThat(sealed).isNotNull()` resolves just
as well as a real assertion does. That last link is what the mutation gate measures
([ADR 0045](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0045-mutation-testing-trust-chain-unit-layer.md)
§ Context).

### Field visibility (ADR 0044)

The guard most directly about operator-blindness is
[`validate_field_visibility.py`](https://github.com/raddatzk/veyq/blob/main/scripts/validate_field_visibility.py)
([ADR 0044](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0044-field-visibility-declared-at-the-field.md)).
Every field in `contracts/api/` must say what the server may read of it, or the build fails:

- `contentEncoding: base64` means **opaque**: the server derives no meaning from the bytes.
- Every other scalar carries `x-veyq-visibility: <class>`. The classes (`id`, `structure`, `measure`, `time`,
  `enum`, `flag`, `token`, `public`, `pii`) are the kinds that
  [security-model § What is encrypted vs. server-visible](https://github.com/raddatzk/veyq/blob/main/docs/crosscutting/security-model.md#what-is-encrypted-vs-server-visible)
  already names.
- `pii`, deliberate sensitive plaintext, also needs an `x-veyq-rationale` that names the mechanism forcing the
  plaintext. The set of `pii` fields is therefore a greppable budget.
- The same rule covers scalar component schemas, every header parameter and every declared response header.

**Its limit, in the ADR's own words: "This checks the contract, not the traffic."** A client that writes plaintext
into a field marked opaque satisfies it completely. It also does not see path or query parameters,
presigned-URL query strings, database column names, error `message` text, undeclared headers, or the S3 object
key. A green run means *no unclassified field in a JSON body, and no unclassified declared header*. It never
means "operator-blind, verified". The traffic is the wire sweep's job.

## Verifying a signed release

A release is identified by its tree. Its deployment recipe is the release's assets, beside a manifest that names
both images by digest, and the publish signs the images, the Helm chart and `veyqctl` keylessly with cosign and
creates the immutable GitHub Release that carries the assets
([ADR 0057](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0057-release-identity-and-deployment-recipe.md),
[ADR 0064](https://github.com/raddatzk/veyq/blob/main/docs/decisions/0064-kubernetes-helm-deployment-target.md)).
The step-by-step check — resolve each tag to a digest once, verify each signature against the one workflow
identity that publishes veyq, then deploy by digest — is on
[Verify a release](/veyq/run/verify-a-release/).

**Nothing on the publish side has been observed yet.** The repository has no remote and no workflow has ever
executed. Every statement about what a publish *does* is therefore a statement about a file, not about a run.
What can be proven locally is the tree-side half: deriving the version, building the images, producing the
release's assets from the tree, and installing an instance from them with `veyqctl`, as the stack end-to-end run
does (ADR 0057 § Consequences).

## Goal

Build [ADR 0157](../docs/decisions/0157-a-kits-layout-has-a-version-and-a-sealed-record-says-which-one-the-account-last-made.md)
and [uc.account.renew-emergency-kit](../docs/features/account/use-cases/uc.account.renew-emergency-kit.md): both kit
writers carry `KIT_LAYOUT` (2 — the sheet with the labelled key), the account keeps a Master-Key-sealed kit record of the
layout it last printed, every flow that makes a kit writes it, and an account whose record is older (or absent) is told
in Settings → Security and once by a dismissible shell notice that a clearer kit exists — made after proving the
password and the Secret Key, the old kit staying valid.

## Context & constraints

- **Builds on PR raddatzk/veyq#39, on `main` since `f9a03413a`.** That change labels the key "Secret Key · 9 blocks in 3
  lines" (the sheet this CR calls layout 2), adds `shared/ui/secretKeyEntry.ts` and greys every Secret-Key submit until
  the key reads.
- Measured 2026-11-22 on `main` `28e3312c0` (spot-check before phase 1):
  - The template for a per-account sealed document is the **device register**, not the favorites: one blob under the
    Master Key, its own tag `account-device-register`, table `veyq_device_register (account_id UUID PK, FK veyq_user,
    sealed_blob TEXT NULL, revision BIGINT)`, backend `core/account/deviceregister/`, client
    `src/web/src/features/account/deviceRegister.ts`. The record differs on purpose: **last writer wins, no revision, no
    trust mark** (ADR 0157 decision 3) — the favorites' `x-veyq-concurrency: last-writer-wins` with a reason is the shape
    of that annotation.
  - The rotation request already carries the device register and the identity-pin head re-sealed under the new Master
    Key (`RotateAccountKeysRequest.deviceRegister`, `RotationHandler`); the record rides the same way.
  - Kits are made at exactly four places (locator below): the join birth (`TenantJoinView`, session-less register,
    `buildAccount`'s Master Key in hand until it is zeroed), the Server Owner's birth (`admin-web` `SetupView` /
    `setupServer.ts`, Master Key zeroed in the request builder), the rotation ceremony (`KeyRotationPanel`, the kit of
    the NEW key printed before the publish) and the address confirmation (`ConfirmEmailChangeView`, not behind the unlock
    gate: `checkColdCredential` opens the floor's Master Key and zeroes it).
  - A seal purpose is a row in `src/packages/crypto/src/seal.ts` `SEAL_PURPOSES` plus a vector in
    `contracts/crypto/vectors/v1.json` § `seal`, generated by an independent implementation (the vector file's note);
    the conformance test reads both directions.
  - The shell's notices are one at a time (`AppShell.vue`, `otherNoticesOn`); `FinishProfilePrompt` with its scoped
    per-user, per-browser dismissal (`finishProfileDismissed.ts`, `createScopedPreference`) is the pattern for the kit
    notice.
  - Account erasure deletes per-account rows in `AccountPurge.eraseRows`; `scripts/validate_account_erasure_arity.py`
    is red on a table reaching `veyq_user` that is neither deleted there nor cascaded.
- Native apps (V2, on their own branches) make kits once their account flows land; this CR does not touch them. ADR 0157
  § Consequences holds what they owe.

## Decisions (technical, settled here)

1. **Contract.** A new tag `account-kit-record` in `contracts/api/account.openapi.yaml`:
   `GET /api/account/kit-record` → `KitRecord { blob: string | null }` (base64, `maxLength: 65532`, null when never
   written); `PUT /api/account/kit-record` with `KitRecordUpdate { blob }` (required) → `204`. Authenticated, the caller's
   own record only, `x-veyq-concurrency: last-writer-wins` with ADR 0157 decision 3's reason. One shared schema
   `SealedKitRecord` (the same string) is added as an **optional** `kitRecord` to `RegisterAndAcceptTenantInviteRequest`
   (`tenants.openapi.yaml`), `CreateServerOwnerRequest` (`setup.openapi.yaml`) and `RotateAccountKeysRequest`. Optional,
   so a client that predates it still births and rotates; absent means "write nothing", never "clear".
2. **Seal.** Purpose `kit-record` with no binding field (`'kit-record': []` in `SEAL_PURPOSES`, as `master-key`): the
   Master Key is the account's alone, the account has one record, and a birth seals it before the account has an id.
   Plaintext the compact JSON `{"layout":n}`. Sealed with the Master Key the flow holds. A blob that does not open, or JSON without a
   positive integer `layout`, reads as **no record** (layout 1) — never an error on screen.
3. **Backend.** Table `veyq_kit_record (account_id UUID PRIMARY KEY REFERENCES veyq_user, sealed_blob TEXT NOT NULL)`,
   upserted; `GET` answers `{ blob: null }` for no row. The two births store `kitRecord` in the transaction that creates
   the account; the rotation stores it in the commit that installs the new Master Key and replaces a row the old key
   sealed (a rotation without `kitRecord` **deletes** the row: it was sealed under a Master Key that no longer exists,
   and "no record" — layout 1 — is the honest answer). `AccountPurge` deletes the row.
4. **Web, the record.** `src/web/src/features/account/emergencyKit/kitRecord.ts`: `sealKitRecord(masterKey)`,
   `readKitLayout(masterKey)` (GET + open, 1 on no record or no open), `writeKitRecord(masterKey)`. `KIT_LAYOUT` is exported beside `renderKitPdf` in `emergencyKit.ts`; each layout ≥ 2 has one catalog
   sentence `kit.layoutNews.<n>` (EN + DE), and a test asserts a sentence exists for every layout from 2 to
   `KIT_LAYOUT`.
5. **Web, the writers.** The join birth seals the record with `buildAccount`'s Master Key before it is zeroed and puts it
   in the register request; the rotation seals it under the new Master Key into the rotation request; the address
   confirmation seals it with the floor's Master Key — `checkColdCredential` gains an optional `use(masterKey)` step run
   before it zeroes the key (the one change to that helper) — and `PUT`s it once the kit was saved; the renewal flow
   proves with `proveColdCredential` (the vault is unlocked there), renders, and `PUT`s once saved. `EmergencyKitSave`
   emits when the PDF was saved and confirmed kept; each host writes then, never at render.
6. **Web, the suggestion.** A section block in Settings → Security (`security`), `EmergencyKitStatus`: "Your Emergency
   Kit is current" or the older-layout state of the use case's step 2, with **Make a new kit** opening the renewal (a
   dialog holding the password field, `SecretKeyField`, and `EmergencyKitSave` after the proof). A shell notice
   `KitRenewalPrompt` (the `FinishProfilePrompt` pattern, its dismissal a scoped preference per user and browser) shows
   only while the layout is older, only when no other notice is on, and links to the section. The layout is read once
   per unlock and kept in memory, dropped where the vault is cleared; a successful write updates it, so both go at once.
7. **admin-web.** `KIT_LAYOUT` beside its `renderKitPdf` (kept equal to web's; a test in each package pins the number,
   and the two layout codes stay line for line alike). `setupServer.ts` seals the record before it zeroes the Master Key
   and sends it in `createServerOwner`.

## Phases

### Phase 1 — contracts and the seal purpose

Decision 1's operations and schemas; decision 2's purpose in `SEAL_PURPOSES` and its vector, generated independently;
`OperatorBlindProbeTest` classifies the two new operations (a probe: the record is opaque). Write one use of the new
schemas in each generated language before committing (`changes/README.md`, the contracts-phase rule).

**Done when:** `pnpm run generate:api` in `src/web/` and `src/admin-web/`; the contracts guards (`scripts/validate_*.py`)
green; `src/packages/crypto` `pnpm run check` green and `pnpm run mutation --force` run, its exit code in the commit
message; `./gradlew check` red only where this README predicts it for a new tag (`ModuleCompositionTest`) — run it once
and name the reds. The births' and rotation's optional field compiles everywhere (optional, nothing builds it yet).

### Phase 2 — backend

Decision 3: migration (`V<yyyymmddHHMM>__core_kit_record.sql`, its line in `scripts/applied_migrations.sha256`),
entity, store, handler, resource for the tag; the two births and the rotation store or delete the row in their
transaction; `AccountPurge` deletes it. Tests: a member reads and writes only their own record; `GET` before any write is
`{ blob: null }`; a birth with and without `kitRecord`; a rotation with `kitRecord` replaces, without it deletes; the
erasure removes the row (`AccountErasureSliceTest`).

**Done when:** `./gradlew check` green (`src/backend/`), the account-erasure and concurrency guards green.

### Phase 3 — web and admin-web

Decisions 4–7. Tests: `kitRecord.ts` round trip, a foreign or garbled blob reads as layout 1; each writer writes after
save and not at render (the join and owner births through their request body, the rotation through its request, the
address confirmation and the renewal through the `PUT`); the renewal refuses a wrong password or key and renders nothing;
the security block for an older, an absent and a current record; the notice shows once, hides after dismissal, and does
not show while another notice is on; a `kit.layoutNews.<n>` exists for every layout up to `KIT_LAYOUT`.

**Done when:** `pnpm run check` green in `src/web/`, `src/admin-web/` and `src/packages/crypto/`; **browser pass** on the
dev instance (`?devlogin`, German UI): with no record the security block and the notice show; dismiss the notice, reload,
it stays gone; make a new kit with the old kit uploaded into the Secret-Key field; the block then says current and the
notice is gone on a second browser signed into the same account.

### Phase 4 — docs

The use case to **built** with what was run; ADR 0157 `Built: yes`; `en.account.key-model § The kit record` drops
*Planned*; `docs/features/account/_index.md`'s row; the Use pages (EN + DE): `getting-started/emergency-kit.mdx` gets
"When veyq suggests a new kit" (the old one keeps working; how to make the new one), and the help page on a lost kit
is read for a sentence that now contradicts it (`site/src/content/docs/help/lost-emergency-kit.mdx`).

**Done when:** every `scripts/validate_*.py` green; the site builds (`site/`).

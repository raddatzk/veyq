    {{ .Values.storeDomain }}     the bundled object store (its own origin on this target)

{{- if (.Values.gateway.tls.acme | default dict).enabled }}

TLS: this release templates the cert-manager Issuer `veyq-acme` (ACME HTTP-01)
against {{ .Values.gateway.tls.acme.server }}
and stamps it on the Gateway and every tenant ListenerSet — a tenant created later is a certificate order of its own.
It works only if:
    cert-manager 1.21 or later runs in this cluster (without its CRDs this release could not have been created at all)
    with its Gateway API support AND its ListenerSet support on — the latter is ALPHA: config.gatewayAPI.enabled,
    config.gatewayAPI.enableListenerSet and config.featureGates.ListenerSets, all true
    your Gateway API implementation supports ListenerSet — not every released one does yet; without it every
    tenant domain stays without a listener, while the hosts above keep working
    port 80 of every host above, and of every tenant domain, reaches the Gateway
    a tenant's DNS points here BEFORE the tenant is created — cert-manager self-checks reachability, then orders
{{- if contains "staging" .Values.gateway.tls.acme.server }}
This is a STAGING directory: its certificates are not browser-trusted. Switch gateway.tls.acme.server to the
production directory once a test order succeeds — until then every browser refuses the instance.
{{- else }}
Production limits worth knowing before you test here (letsencrypt.org/docs/rate-limits): 5 failed validations per
hostname per hour, 50 new certificates per registered domain per week. The staging directory is the one-line switch.
{{- end }}
Watch the orders:
    kubectl -n {{ .Release.Namespace }} get issuer veyq-acme
    kubectl -n {{ .Release.Namespace }} get certificate
    kubectl -n {{ .Release.Namespace }} get listenersets
{{- else if eq .Values.gateway.tls.mode "none" }}

TLS: gateway.tls.mode is `none`. Nothing in this release obtains a certificate, and the Gateway listens on plain
HTTP only. Unless something upstream terminates TLS for every host above, the refresh cookie (Secure) is never sent
back and every mailed link points at https — an instance that boots and then silently breaks. See gateway.tls in
values.yaml.
{{- else if eq .Values.gateway.tls.mode "per-domain" }}

TLS: gateway.tls.mode is `per-domain` without the chart's ACME issuer — your own issuer must fill the Secrets the
Gateway's listeners and every tenant ListenerSet reference (each named after its route). Every tenant domain needs
a Gateway API implementation that supports ListenerSet; not every released one does yet.
{{- end }}

{{- if eq (include "veyq.clientPortSource" .) "proxyProtocol" }}

Client port: app.clientPort.source is `proxyProtocol`. The app now closes every connection that does not open with a
PROXY header, so your Gateway must send PROXY (v1 or v2) to the app's routes — and ONLY to them: never to the object
store's route, or every upload and download fails. Aim it at the routes by label (app.kubernetes.io/component: app on
the chart's route, and the backend's owner label on the tenant routes it projects), never at the whole Gateway. The
probes poll the admin listener meanwhile; they prove the process and the database, not the public listener.
{{- else if eq (include "veyq.clientPortSource" .) "header" }}

Client port: app.clientPort.source is `header`. veyq believes the port in {{ (.Values.app.clientPort | default dict).header | default "X-Veyq-Client-Addr" }} — make sure your edge
OVERWRITES it on every request. A header the edge passes through is one any client writes.
{{- end }}

Every route of this release — the chart's `veyq-*` and the `veyq-tenant-*` ones the backend projects — and whether
the Gateway accepted it:
    kubectl -n {{ .Release.Namespace }} get httproutes,listenersets

{{- if .Values.garage.enabled }}
Before the first tenant, the object store must have passed its check. With nothing saved, the app sets the
bundled store itself after it has provisioned Garage, and checks it; read the result in the same console (over the
port-forward above) under Server → Object store, where "Check store" runs it again and a store of your own can be
saved instead. Tenants can be created only after a passed check. For the bundled Garage the same page shows how its background
provisioning went — the public origin answers no Server-Owner operation, so this is the place to read it;
`veyq-admin store check` provisions it again and prints every step.
{{- else }}
Before the first tenant, set the object store in the same console (over the port-forward above): open
Server → Object store and enter a store of your own (garage.enabled is false, so this release brings none and the
console offers no bundled one), save it, then "Check store". Tenants can be created only after a passed check.
{{- if .Values.backup.enabled }}
The backup gate cannot open that store's key (it is sealed under the KEK the gate never reads): name a Secret with
its endpoint, bucket and a key pair that can list it in backup.store.existingSecret, or the first capture fails
naming the value.
{{- end }}
If garage.enabled was true before, its claims (meta-/data-/snapshots-veyq-garage-0) remain: deleting them deletes the objects.

{{- if .Values.backup.enabled }}

Backups: the init container `backup-gate` captures the database and an index of the store onto the claim
{{ .Values.backup.existingClaim }} whenever the pod starts a different release (or a new backup.request), BEFORE the
app migrates, and keeps the newest {{ .Values.backup.keep }}, none older than B — the days the Server Owner sets in the
admin console (30 until set); the gate and the daily CronJob veyq-backup-prune delete every capture past B, the newest
too, so a copy you need longer is one you move off the claim, and delete yourself by B. The app is down while it runs, and a failed or refused
gate keeps it down with its data untouched. So upgrade with a timeout above the capture time, and watch the pod:
    helm upgrade --wait --timeout 15m …            (without --wait, helm reports success before the gate ran)
    under Flux: spec.timeout above the capture time; under Argo CD the Deployment reports ProgressDeadlineExceeded
    kubectl -n {{ .Release.Namespace }} logs deploy/veyq-app -c backup-gate
{{- if .Values.app.configSecret.existingSecret }}
The gate never reads the config-secret key, which is your Secret {{ .Values.app.configSecret.existingSecret }}: keep
the file you made it from apart from the claim — see https://veyq.app/run/backup-and-restore/ (and keep
the store's own versioning on: the gate indexes the objects, it does not copy them).
{{- else }}
The gate never reads the config-secret key: export it once, now, and keep it apart from the claim — see
https://veyq.app/run/backup-and-restore/ (and keep the store's own versioning on: the gate indexes
the objects, it does not copy them).
{{- end }}
{{- else }}

Backups: backup.enabled is false. Nothing captures the database before a release change migrates it: taking that
backup before every upgrade is yours, by the hand procedure on https://veyq.app/run/upgrade/.
{{- end }}
{{- if not .Values.networkPolicy.enabled }}

networkPolicy.enabled is false: nothing confines who reaches the app's port. Any pod in the cluster can then write
the whole X-Forwarded-For header, and no setting in veyq can tell it apart from your Gateway, so the per-IP rate
limit (and, once it is built, the record of a guest's writes) can carry a forged address (ADR 0094 decision 6). The
same holds with a CNI that enforces no NetworkPolicy.
{{- end }}
